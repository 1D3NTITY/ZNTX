# zntx — "Die Seite lebt sichtbar" + interaktives Live-Terminal

**Stand:** 2026-09-03 · **Entscheidung:** Luis, beide Bausteine (Live-Daten sichtbar + Terminal)

## Ausgangsdiagnose

Mehrere Runden visueller Politur (Alumica-Gradient, Glass-Chrome, Aurora-Blobs, Wort-für-Wort-
Animation, Konzept F "Zwei Racks") haben den gewünschten Wow-Effekt nicht erzeugt. Grund ist
nicht die Optik, sondern was die Optik zeigt:

Die Status-Endpoints liefern **echte, bewegliche Betriebsdaten**:

```
ravepuls     operational   last_deploy 2026-08-24   last_sync 2026-09-03T04:00:13Z
buchhaltung  operational   last_deploy 2026-08-23   last_sync null
matrix-chat  operational   uptime_since 2026-08-20
qntx         operational   (bewusst reduziert, Kapitalrisiko)
```

`formatLiveStatus()` (lib/labels.ts:64) baut daraus bereits fertige Zeilen wie
„Deploy vor 10 Tagen · Sync vor 6 Std" — und `rack-slot.tsx:62` **verwirft sie** und rendert
stattdessen einen 2×2-Pixel-Punkt mit `title`-Tooltip.

Folge: Ein Besucher kann in den ersten Sekunden nicht unterscheiden, ob hier echte laufende
Infrastruktur steht oder ein hübsches statisches Portfolio. Genau die Unterscheidbarkeit ist
aber das Einzige, was keine gekaufte/generierte Vorlage kopieren kann — weil dahinter echte
Maschinen stehen müssen. Mehr Gradient kann das nicht heilen.

**Leitprinzip:** Nie erfundene Daten (bestehende Regel aus lib/status.ts und content.ts). Wo
kein Endpoint existiert (motortown, wcp-arma, n8n-automation, zntx selbst), wird das ehrlich
benannt statt kaschiert.

## Baustein 1 — Live-Daten sichtbar machen

**1a. `lib/status.ts`** — Rückgabe wird zum Snapshot mit Zeitstempel:
```ts
export type StatusSnapshot = {
  statuses: Record<string, LiveStatus | null>;
  fetchedAt: string;   // ISO, serverseitig gesetzt
};
export async function getProjectStatuses(): Promise<StatusSnapshot>
```
Begründung: Ein Snapshot hat fachlich immer einen Zeitpunkt; ohne ihn lässt sich „das ist
gerade abgefragt worden" nicht ehrlich behaupten. Zwei Aufrufstellen ziehen nach
(`ops-dashboard.tsx`, `app/projekte/[slug]/page.tsx`).

Achtung Ehrlichkeit: `revalidate: 60` heißt, die Daten sind bis zu 60 s alt. Beschriftung
deshalb „Stand HH:MM:SS", nicht „jetzt live".

**1b. `components/rack-slot.tsx`** — die bereits berechnete Detailzeile wird gerendert statt
verworfen: dritte Zeile unter Name/Meta, mono, klein, gedämpft
(z. B. „Deploy vor 10 Tagen · Sync vor 6 Std" / „Uptime seit 20. Aug. 2026").
Slots ohne Live-Daten bekommen keine Platzhalterzeile (kein Layout-Sprung, keine Fake-Info).
LED bleibt, bekommt zusätzlich ein `title` mit derselben Info für Maus-Nutzer.

**1c. `components/ops-dashboard.tsx`** — unter der Status-Legende eine dezente Zeile:
„Live-Daten abgefragt um HH:MM:SS · aktualisiert sich alle 60 Sekunden".
Serverseitig formatiert und als String durchgereicht — **kein** `Date.now()` im Client-Render
(sonst Hydration-Mismatch, siehe wiederkehrende Bug-Klasse dieser Session).

## Baustein 2 — Interaktives Live-Terminal

**Neu: `components/live-terminal.tsx`** (Client Component)

Ein echtes Terminal auf der Startseite, das auf getippte Befehle mit **den echten Serverdaten**
antwortet — nicht mit Attrappen-Strings. Passt zur bereits etablierten Terminal-Identität der
Seite (`zntx_`-Cursor im Hero, `kontakt.sh`-Fensterchrome im Kontaktformular).

**Datenweg:** Der Snapshot aus Baustein 1a wird als Prop vom Server in die Client-Komponente
gereicht. Kein neuer API-Endpoint, kein Client-Polling (YAGNI + keine zusätzliche
Angriffsfläche, keine Rate-Limit-Frage). Das Terminal antwortet aus dem Snapshot und nennt
dessen Zeitstempel.

**Befehle** (bewusst klein gehalten, alle aus vorhandenen Daten bedienbar):

| Befehl | Antwort |
|---|---|
| `help` | Befehlsliste |
| `status` | alle Systeme mit Live-Zustand + Detailzeile |
| `status <id>` | ein System im Detail |
| `systems` | alle 8 Systeme + Server-Zuordnung aus `content.ts` |
| `uptime` | Systeme mit bekannter Laufzeit |
| `whoami` | Kurzprofil aus `BIO` |
| `clear` | Ausgabe leeren |

Unbekannter Befehl → Hinweis auf `help`. Systeme ohne Endpoint antworten explizit
„kein HTTP-Endpoint (Gameserver / archiviert)" statt einen Status zu erfinden.

**Verhalten/Qualität:**
- Fortschreitende Verbesserung: Ohne JS bleibt die Seite vollständig nutzbar, alle Infos stehen
  weiterhin in den Racks. Das Terminal ist additiv, nie einzige Informationsquelle.
- A11y: `<input>` mit visuell verstecktem `<label>`, Ausgabe-Region mit `aria-live="polite"`,
  kein Focus-Trap, vollständig per Tastatur bedienbar (ist es naturgemäß), sichtbarer
  Focus-Ring. Klick auf das Fenster fokussiert das Eingabefeld.
- Reduced Motion: kein Tipp-/Caret-Effekt, Ausgabe erscheint sofort.
- Hydration: Erstzustand serverseitig identisch (statische Begrüßungszeile aus Prop), kein
  client-abhängiger `initial`-Zweig — die in dieser Session zweimal aufgetretene Bug-Klasse
  wird gezielt vermieden.
- Eingabe wird nie als HTML interpretiert (reines React-Text-Rendering, kein
  `dangerouslySetInnerHTML`).

**Platzierung:** Eigener Abschnitt zwischen Status-Legende und den beiden Racks — direkt dort,
wo der Besucher ohnehin auf die Live-Frage stößt.

## Verifikation

1. `bun run lint` + `bun run build`.
2. Playwright: Startseite Desktop + Mobile, Rack-Slots zeigen echte Detailzeilen.
3. Terminal-Funktionstest: `help`, `status`, `status ravepuls`, `status motortown`
   (muss ehrlich „kein Endpoint" sagen), `systems`, `uptime`, `whoami`, `clear`,
   Unsinnseingabe → Hinweis.
4. Tastaturbedienung: Tab erreicht das Eingabefeld, Enter löst aus, Focus-Ring sichtbar.
5. Reduced-Motion-Kontext: Inhalt sofort da, keine Animation.
6. Kein Hydration-Warning im Dev-Log, keine Konsolenfehler.
7. Ohne JavaScript: Seite bleibt vollständig, Racks tragen alle Infos.
8. Commit (kein Extra-Approval, Session-Regel), Redeploy **nur** nach frischer Bestätigung.
